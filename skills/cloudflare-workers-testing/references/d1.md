# D1 with migrations

Apply the project's migrations to fresh local D1 storage before inserting fixtures. Assert behavior through a Worker request and inspect rows when that helps identify a failure. Use the same migration directory and binding name as the Worker.

## Vitest plugin

Read migrations while Vitest evaluates configuration in Node.js. Pass them to the Workers runtime through a test-only binding, then apply them in setup or before each test:

```ts
// vitest.config.ts
import path from "node:path";
import { cloudflareTest, readD1Migrations } from "@cloudflare/vitest-plugin";
import { defineConfig } from "vitest/config";

export default defineConfig({
  plugins: [cloudflareTest(async () => ({
    wrangler: { configPath: "./wrangler.jsonc" },
    miniflare: {
      bindings: {
        TEST_MIGRATIONS: await readD1Migrations(path.join(__dirname, "migrations")),
      },
    },
  }))],
});
```

```js
// test/d1.spec.js
import { env, exports } from "cloudflare:workers";
import { applyD1Migrations } from "cloudflare:test";
import { beforeEach, expect, test } from "vitest";

beforeEach(async () => {
  await applyD1Migrations(env.DB, env.TEST_MIGRATIONS);
});

test("reads a migrated table", async () => {
  await env.DB.prepare("INSERT INTO users (id, name) VALUES (?, ?)")
    .bind("123", "Ada").run();
  const response = await exports.default.fetch("https://example.com/users/123");
  expect(await response.json()).toEqual({ id: "123", name: "Ada" });
});
```

`applyD1Migrations()` tracks applied files in a migrations table. The plugin isolates storage per test file, so call `reset()` between tests when rows must not carry over, then reapply migrations. In TypeScript tests, add `TEST_MIGRATIONS` to the `cloudflare:workers` `ProvidedEnv` declaration.

## Wrangler test harness

`worker.applyD1Migrations(bindingName)` reads `migrations_dir` and `migrations_pattern` from Wrangler configuration, or `.sql` files from its default `migrations` directory. Apply migrations after each storage reset and before seeding:

```ts
const worker = server.getWorker("api-worker");

beforeEach(async () => {
  await worker.applyD1Migrations("DB");
  const env = await worker.getEnv();
  await env.DB.prepare("INSERT INTO users (id, name) VALUES (?, ?)")
    .bind("123", "Ada").run();
});

test("reads a migrated table", async () => {
  const response = await worker.fetch("/users/123");
  expect(await response.json()).toEqual({ id: "123", name: "Ada" });
});
```

Use the shared harness `listen()`/`reset()`/`close()` lifecycle. If a migration fails, fix the migration or fixture setup before asserting routes; do not create tables ad hoc in the test.
